## Rate-limit approach

Run deterministic and database checks without providers first. Then run live requests sequentially, with a minimum interval between OpenRouter requests, stop on rate-limit responses, reuse a small number of chats across related checks, and track tokens/call count. Never retry tool actions automatically after a provider failure.

## Personalization boundaries

Automatic dreaming covers answer length, answer order, comparison style and decision priority. Additional free-text instructions remain a Settings-only edit. Operational settings still require explicit confirmation. Routine dispatch facts, temporary requests, assistant text, quoted examples, and unsupported preferences do not become personalization. Existing saved or deliberately removed fields remain protected from inferred replacement.

## Findings and verification results

### Changes made after observed failures

1. Dreaming now saves validated response preferences and advances the extraction marker atomically. It creates no new personalization approval rows. Existing saved choices and explicit removals stay protected.
2. Added the exact extraction JSON schema to the prompt after Nemotron returned the wrong evidence key. Invalid output leaves the batch pending for a later run.
3. Clear preference-only requests such as “Keep answers short for me” use the validated personalization tool directly. The model previously acknowledged this without saving it. Mixed dispatch questions still go through RAG.
4. Current saved personalization takes precedence over older chat style requests. A live follow-up returned a concise, cited answer after Brief was saved.
5. Pure incentive-cap requests now produce a validated pending change directly. The model previously referred to a Confirm button without creating a proposal. Operational changes still need confirmation; an out-of-range ₹600 request was rejected.
6. Handover drafts receive application-recorded confirmations and cancellations separately from model summaries. Reopened chats are bounded to the shift's start/end times, and summaries spanning other shifts are excluded from draft context.
7. Alert popup position follows the composer's height, so pending-change controls are accessible. Confirm and Cancel were exercised in the actual browser.
8. Batching guidance explicitly requires route checks even within one zone. Same-zone orders are candidates until every required policy check is verified.
9. Rate limits get a specific frontend message. The draft is restored, the composer unlocks, and the provider or write tools are never automatically replayed.
10. Updated provider configuration, docs, test isolation, and the batching starter. Tests disable dotenv loading and clear provider credentials before collection.

### How far this verification goes

Live model checks use a small synthetic policy corpus, real Jina embeddings and a fresh local PostgreSQL schema. The automated suite also exercises the repository corpus/chunking contracts and provider error cases. Long transcripts, conflicting workers, rollback, malformed extraction and precise timing boundaries are deterministic tests, rather than expensive live model runs.

The configured local database role originally lacked access to `app.shifts`, `app.manager_personalization` and `app.alert_events`. After user approval, SELECT, INSERT, UPDATE and DELETE were granted on only those three existing tables. Configured-role table access, schema usage and scenario-table TRUNCATE access were then verified. No data, environment file or future-table privileges were changed. The main app was restarted using the configured database URL, and its homepage returned HTTP 200.

The restarted main app also passed a fresh Chrome check of Personalization, Handover and the favicon (HTTP 200), with no unhandled JavaScript errors and no model requests.

The free model returned a 429 after 32 successful paced QA requests. Calls stopped immediately. One bounded retest after more than five minutes of cooldown also returned 429; no further live calls were sent. The final live batching retest remains unconfirmed. The recorded QA total is 34 requests, 32 successful and two rate-limited, with 102,761 reported tokens and zero reported cost. Earlier provider smoke checks used another seven requests and 1,897 tokens. External capacity remains outside application control, so this report does not promise that every future model request will succeed.

### Personalization intentionally not learned

- Free-text additional instructions can be saved in Settings. Dreaming currently learns only the four typed preference categories.
- Temporary instructions, dispatch facts, unsupported preferences, quotes, negated requests and assistant text do not become lasting preferences.
- Dreaming does not overwrite a saved choice or resurrect a deliberately removed preference. Explicit chat requests or Settings edits can change it.
- Incentive caps, alert thresholds, batching settings and dispatch actions are operational choices. Personalization cannot change them or relax policy.
- The legacy weekly digest and resolution-note retrieval are not active chat features. Operational Suggestions are hidden in the UI, although the review still records valid proposals and answer issues.
